# P1a 사전 등록 — H의 구성타당도

> **이 문서는 §9 P1a를 옮겨 적은 것이 아니라 고정한 것이다.** 배터리 B(§9 일정 G2, W10)를 돌리기 **전에** 설계를 못 박아, 결과를 본 뒤 설계를 바꾸는 일을 막는다. 그렇게 바꾸면 검증이 아니다(§12 "P1a 사전 등록").

**등록 시각**: 2026-09-11 (G0, §9 일정 W1–3)
**등록 시점 `prd.md` 버전**: v3.7.9
**등록 시점 계약**: §2.5(백분위·분위·산술) · §2.7(이력) · §3.1(H) · §9 P1a
**평가 예정**: 배터리 B — G2 go/no-go (§9 일정 W10)

## 1. 무엇을 묻는가

**H가 `chg_commits` 단독보다 이후 6개월 개발자 개입을 더 잘 예측하는가.**

이 질문이 필요한 이유: `H = 100·√(pct(cx) × pct(chg_commits))`는 `chg_commits`를 **성분으로 갖는다**. 그래서 "H 상위 파일이 앞으로도 많이 변경된다"는 관찰은 결합식의 가치를 증명하지 못한다 — 활동이 지속된다는 사실만 다시 말할 뿐이다. 물어야 하는 것은 **증분**이다: 복잡도 프록시를 곱한 것이 변경 이력 하나보다 나은가.

이것은 **구성타당도**(H가 재려는 것을 재는가)다. 결과타당도(H 상위가 결함 수정 커밋을 더 받는가)는 P1b가 따로 진다.

## 2. 기준선 넷

같은 리포·같은 창에서 넷을 나란히 돌린다. 하나라도 빼지 않는다.

| # | 기준선 | 상위 10% 집합의 정의 |
|---|---|---|
| 1 | `random` | 적격 파일에서 무작위 10% (고정 시드, 시드를 기록한다) |
| 2 | `cx-only` | `pct_active,lang(cx)` 상위 10% |
| 3 | `chg-only` | `pct_active(chg_commits)` 상위 10% |
| 4 | `H` | `H` 상위 10% (§3.1) |

- 모집단은 `active`(§2.5) — `chg_commits ≥ 1`.
- 상위 10% 멤버십은 `pct ≥ 0.90`, 동점 tie-break는 `priority desc, path asc, id asc`(D28).
- 백분위·분위·임계 비교는 **반올림 전 정확값**으로 한다(§2.5 산술 계약, D115). 직렬화된 값으로 자르면 경계에서 집합이 흔들린다.

**주 지표**: 각 집합의 6개월 개입 리프트.

```
Lift(S) = P(개입 | 파일 ∈ S) / P(개입 | 파일 ∉ S)
```

**판정 대상은 증분이다**: `Lift(H) − Lift(chg-only)`. `Lift(H)` 하나만 크면 아무것도 말하지 않는다.

## 3. 개입(intervention)의 정의와 제외 규칙 다섯

**개입** = 결과 창 안에서 그 파일을 만진 비머지 커밋이 ≥ 1건. 창과 커밋 자격은 §2.7을 따른다(머지 커밋 제외, rename 매핑 적용).

아래 다섯에 해당하는 변경은 **개입으로 세지 않는다**. 세면 "누가 파일을 건드렸나"가 아니라 "도구가 파일을 건드렸나"를 재게 된다.

1. **공백만 변경** — 내용 토큰 변화 0.
2. **`@Generated`/generated 경로만** — `build/generated/` 유래 및 `@Generated` 표시 파일(§2.2 `bytecode_scope`의 제외와 같은 선).
3. **내용 변경 없는 대량 rename** — rename 매핑이 흡수하는 이동(§2.7 유사도 60).
4. **의존성·벤더 경로만** — `build.gradle*`, `pom.xml`, `libs/`, lockfile.
5. **위 넷의 조합만으로 이루어진 커밋** — 커밋 안에 실질 변경이 하나도 없으면 그 커밋은 개입이 아니다.

제외는 **커밋×파일 단위**로 적용한다. 한 커밋이 어떤 파일은 실질 변경하고 어떤 파일은 공백만 바꿨다면 앞의 파일에만 개입을 센다.

## 4. 검열 계약 — 미완료 관찰을 세지 않는다

관찰창이 6개월인데 최근 파일은 6개월이 지나지 않았다. 그것을 "개입 없음"으로 세면 최근 코호트가 전부 음성이 되어 리프트가 망가진다.

| 파라미터 | 값 | 뜻 |
|---|---|---|
| `evaluation_cutoff` | 배터리 B 실행 전에 **고정**하고 여기 기록한다 | 관찰의 끝 |
| `followup_days` | **180** | 결과 창 길이 |
| 적격 코호트 | `index_time ≤ evaluation_cutoff − 180d` | **6개월 완전 관측만** |
| 결과 창 | `[index_time, index_time + 180d]` | 개입을 세는 구간 |

- `index_time` = 그 리포 스캔의 `window_anchor`(HEAD 커미터 시각, §2.7·D25). 실행 시각이 아니다 — 같은 HEAD를 언제 재도 같은 코호트가 나와야 한다.
- 적격 코호트에 들지 못한 파일은 **분석에서 제외**한다. 음성으로 세지 않는다.
- `evaluation_cutoff`는 리포마다 다를 수 있다(리포마다 HEAD가 다르다). 리포별 값을 전부 기록한다.

## 5. 통계

- 모든 리프트에 **부트스트랩 95% CI**. 재표본 단위는 **파일**, 반복 10,000회, 고정 시드(기록한다).
- **리포별 값을 전부 적고 중앙값을 함께 적는다.** 합치지 않는다.
- 증분 리프트 `Lift(H) − Lift(chg-only)`에도 같은 방식으로 CI를 낸다(쌍 부트스트랩 — 같은 재표본에서 두 리프트를 함께 계산한다).

**수치는 통계적 결론이 아니라 go/no-go 휴리스틱이다.** 리포 3개는 표본이 아니다(§9 통계 기록).

## 6. 깨짐 기준 — 미리 정한다

| 조건 | 조치 |
|---|---|
| 3개 리포 중 **2개 미만**에서 `Lift(H) > Lift(chg-only)` | H 식 재설계 — 복잡도 프록시 또는 결합 함수 |
| 증분 리프트 **중앙값 ≤ 0** | 같음 |

**둘 중 하나라도 걸리면 재설계한다.** 어느 쪽도 "다시 재본다"가 아니다.

P1a 실패의 파급: 핫스팟이 개입을 예측하지 못하면 헤드라인이 무너진다. G2 전에는 수정 워크플로에 착수하지 않는다(§12).

## 7. 바꾸지 않는다 — 그리고 바꿔야 한다면

**배터리 B 전에 이 문서를 바꾸지 않는다.** 결과를 본 뒤 설계를 바꾸면 검증이 아니라 사후 맞춤이다.

불가피한 변경이 생기면:

1. **배터리 B를 돌리기 전에** 바꾼다. 결과를 본 뒤의 변경은 이 사전 등록을 무효로 만든다.
2. 이 문서 아래 **변경 이력** 절에 항목을 추가한다 — 무엇을, 왜, 언제, 어느 `prd.md` 버전에서.
3. 계약이 움직이는 변경이면 `prd.md` §0에 항목과 D 번호를 남긴다(CLAUDE.md §5).
4. **이전 판을 지우지 않는다.** 취소선과 대체 참조로 남긴다.
5. 배터리 B 결과 보고서에 "사전 등록이 n회 개정됐다"를 명시한다.
